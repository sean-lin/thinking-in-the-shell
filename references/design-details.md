# 设计决策详情

> SKILL.md §2 的完整展开：各理念的完整论证、Conway's Law、Docker 隔离案例、延伸原则与细则。涉及架构选型、抽象设计、技术决策、三方库选型时阅读。

设计的第一步不是写代码，而是为系统建立一组稳定、精确、共享的概念；概念即结构，实现可以粗粝，但概念必须清晰。

## 2.1 系统设计与技术决策核心理念

1. **充分了解场景，选择合适抽象**：在做设计决策前，尽可能了解业务场景和技术约束，然后选择一个合适的设计抽象来满足业务需求。不急于动手，先把问题域搞清楚。

   场景不仅包括业务需求和技术栈，也包括组织结构与团队边界。多系统合作时，接口、模块与服务的划分往往受团队关系影响（Conway's Law）。与其强行设计一个违背组织沟通结构的理想架构，不如先让抽象与现实团队边界合理匹配，再逐步演进。
2. **确立抽象后严格遵守，不因方便而妥协**：一旦确认并确立了抽象框架，严格遵守其边界和约束，绝不因为"方便实现"或"快速修复"而突破框架。即使面临短期成本（如更多代码量、更多编译错误），也要维护抽象的完整性。
3. **抽象不适合时果断重建，绝不妥协于旧方案**：如果整个抽象已不适合业务场景，果断推倒重来，设计合理的过渡方案，方向一定是走向新方案，绝不在旧方案上无限打补丁。
4. **优先选择粗粒度、通用、覆盖面大的最终防线，避免精巧脆弱、需要穷举适配的方案**：设计安全、隔离、恢复或错误处理机制时，先找一条简单甚至粗糙、但能覆盖绝大多数场景的兜底边界；不要为了追求每个 case 都精致，而引入大量条件分支、环境依赖或领域特定适配。这条防线应当是清晰的边界（隔离、终止、降级、明确失败），而不是静默吞错的防御性代码。

   这条原则适用于系统与不可控外部组件之间的边界；对于自己实现的代码，仍应精确理解其行为，不以此原则替代对根因的追究。

   > 例如：各类编程系统为运行时隔离尝试过 Python venv、Node `node_modules`、chroot 等依赖环境精细适配的方案，最终胜出的是 Docker——它并不完美，但以操作系统级边界提供了覆盖面最大、语义最简单的隔离。项目早期的 "Release 产物不带 Inspector"、"进程退出即释放全部状态" 都属于同一思路：用一个粗糙但全覆盖的边界，替代对无数运行时细节的穷举式适配。

延伸原则：

- **面向未来**：综合考虑外部生态发展，优先选择长期有利、产生更少技术债的方案。
- **功能优先于形式**：目标是让功能正常工作，而非仅仅通过编译或测试等校验手段。
- **宁可多写代码，不可破坏抽象**：比如宁可写更多类型守卫代码，也不接受无法正确收窄的类型设计。
- **复用团队资产，但不被沉没成本绑架**：优先复用已有且兼容的资产（库、协议、构建经验）；旧抽象已明显不适配时果断重建并设计一次性迁移方案，不长期维护双轨实现。

## 2.1.1 快速原型与占位策略

- 复杂设计先通过最小可运行闭环验证，不要一次实现所有功能。
- 抽象边界确立后，允许用占位、stub、`not_supported` 等最小实现占位；占位是快速原型阶段的临时策略，走向成熟、对外发布或交付他人试用前，应有计划地替换为真实实现。
- 对当前不需要或价值低的功能，优先删除或明确冻结，而不是为了「完整」而过设计。

## 2.2 功能正常工作优先于通过编译校验

- 类型修复和测试通过是手段，不是目的。
- 不能为了消除编译错误而引入运行时不工作的代码（例如添加空类型声明来掩盖缺失的依赖）。
- 修复方案必须真正解决问题，而不是掩盖问题。

## 2.3 卓越设计与第一性原则

**追求卓越，遵循最佳实践**：

- 设计和编码应以卓越为目标，而非仅满足功能需求。代码和架构设计应符合所用语言、框架的最佳实践，并与业界发展方向保持一致。
- 技术选型时选择符合主流、有长期社区支撑的方向，避免引入正在衰退或偏离生态主流的技术。

**三方库选型与导入纪律**：

- 三方库选型综合考量：业界流行度（生态成熟度、维护活跃度）、与团队技术栈的适配性、长期演进风险。不因"已在用"或"快速能跑"就轻易选型，选型时应明确记录决策依据。
- 三方库组件必须从库本身的官方标准包路径导入，禁止从别名或内部路径导入——会导致类型不匹配、导出缺失和版本升级后的隐性断裂。团队应维护"允许导入路径"清单或 lint 规则，防止误入。

**第一性原则设计**：

- 不要因为已有代码这样写、或业界惯常做法如此，就认为这是最优方案。每次设计都应从业务的实际需求出发：我们在解决什么业务问题？有没有比当前方案更直接、更简洁的解法？
- 在充分理解问题域之后，再结合现有代码评估：是在现有方案上迭代演进，还是推倒重做更合算。演进与重做都是合理选择，关键是基于对问题的深入理解，而非路径依赖。

## 2.3.1 场景选择

- 设计前先明确主要消费方（AI Agent / CI / 开发者 / 终端用户）。
- 跨平台/多 transport 项目先选一个能跑通的真实场景做闭环，其他路径明确冻结。

## 2.4 数据驱动的弹性设计

在符合业务需求的前提下，优先设计数据驱动、配置驱动的方案，而非硬编码流程。弹性设计使系统能以较低成本应对业务的剧烈变化——修改数据或配置，而非修改代码逻辑。

## 2.5 重视落盘数据与 API 契约

代码是容易改变的，落盘数据（数据库 schema、持久化格式）和 API 协议（接口契约、字段语义）一旦上线则难以变更，改变它们往往需要迁移脚本、版本兼容层和跨团队协调。因此：

- 数据结构设计和 API 设计需要投入比代码实现更多的思考；
- 数据模型要准确反映业务语义，避免过度耦合实现细节；
- API 字段命名和语义要清晰、稳定，向前兼容性要在设计阶段考虑；
- 接口和协议优先于 UI，而落盘数据与 API 协议正是系统最稳定的契约：UI 是易变的，不同用户、场景或时代可能使用完全不同的 UI；落盘数据格式与 API 协议一旦上线则难以变更。因此先为这两者投入精力，UI 只是其上的消费形式；
- 宁可让代码复杂一点，也要保持数据契约的清晰和稳定。

## 2.6 选择正确的工具与抽象层：似远实近

**坚持以正确的方式做事。** 如果存在更优雅、更准确的方案，即使技术上更复杂，也应该选择它，而不是用更简单但充满边界条件的方案凑合。这样做看似绕远，实则更快到达——不会在特殊情况的泥潭里反复挣扎。

> 本节是 SKILL.md 开头「抵制『让信号变绿』的捷径」共同模式在工具与抽象层选择上的实例；同一模式的其他实例：本文件 §2.2（空类型声明掩盖缺失依赖）、`debugging-playbook.md` §3.2（防御性兜底）与 §3.3（反模式清单）。

两个典型场景：

- **批量代码转换**：批量修改代码时，先评估简单字符串替换是否够用。一旦发现需要应对的特殊情况越来越多、正则越写越复杂，就应果断切换到 AST 工具（如 jscodeshift、ts-morph）——在代码结构层操作，天然准确，不存在文本匹配的二义性。绝不要反复调试越来越复杂的文本操作脚本；实在不值得 AST 的情况下，直接逐文件手动修改反而比复杂正则更快。
- **规则系统设计**：需要设计一个规则/配置系统时，认真考虑是否值得设计一个语义清晰的 DSL（哪怕图灵完备）并严肃实现它——这往往远好于枚举各种 case、编写大量特定逻辑模板、再用 if/else 拼凑起来的方案。后者看起来"简单快速"，实际上随着规则增加，维护成本呈指数上升，且难以复用和测试。选择正确的抽象，才是真正的捷径。

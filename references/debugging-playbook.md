# 调试方法论详情

> SKILL.md §3 的完整展开：四步闭环表格、诊断工具分层（L1–L4）、完整反模式清单与跨场景示例。进行 bug 排查、失败调试、根因定位时阅读。

## 3.1 举一反三：排查同类普遍性

修复一个 bug 或发现一个错误写法时，**不能只修复眼前这一处**。必须立即评估：这个问题是孤立的，还是具有普遍性？其他模块、其他文件是否存在相同或类似的写法？

操作步骤：

1. 识别问题的本质（错误模式、错误调用方式、错误假设）；
2. 在代码库中搜索相同模式（grep 关键词、函数名、调用方式）；
3. 逐一确认是否适用，批量修复所有受影响位置；
4. 修复后确认无遗漏，而非仅解决当前报告的问题点。

**不做举一反三的代价**：相同的 bug 在不同位置重复被发现，每次都需要单独修复，且往往在生产环境触发后才被注意到。

## 3.2 溯根究底：不放过错误，不轻易兜底

遇到任何错误、异常或意外行为，**必须找到根因，而不是用防御性代码绕过它**。

此处的「不兜底」反对的是：对自己代码的行为缺乏把控，用 `try/catch`、默认值或空判断来掩盖思考不足。对于不可控的第三方代码、外部依赖或跨进程边界，设计粗粒度的最终防线（如 Docker 隔离、进程沙盒、明确失败边界）正是系统级追求卓越的表现。

- **不轻易写兜底性 `try/catch`**：空 catch 或宽泛 catch 会掩盖真实问题，让 bug 在静默中持续存在。除非明确知道某类异常是预期的（如用户取消操作、网络超时重试），否则不要用 catch 吞掉异常。
- **不轻易做防御性编程**：对"理论上不会发生"的情况加 null check、默认值兜底，看起来安全，实则是在为错误数据流/错误调用路径保驾护航，让真正的 bug 悄悄溜走。
- **根据根因决定处理方案**：找到根因后，根据问题性质选择合适的修复层级——是调用方错误、接口契约不明确、还是底层实现缺陷？在正确的层级修复，而不是在离症状最近的位置加防御代码。

典型反例：API 返回了意外格式，不应直接加 `?? []` 兜底，而应先确认是接口变更、数据问题还是本地解析错误，再决定修法。

## 3.3 复现优先：调试四步闭环

调试任何失败（应用 bug、测试失败、生产问题）时，**复现问题**是不可绕过的第一步。哪怕通过阅读代码已经定位到疑似根因，仍必须按四步闭环，而不是直接动手改代码：

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1. 复现 | 用独立于被测流程的工具（浏览器 DevTools / MCP、手动操作、调试器断点、curl 直连 API）走一遍用户路径，观察到**真实可见**的失败现象 | 现象记录（截图、DOM 快照、事件链、请求/响应、堆栈） |
| 2. 固化 | 把复现步骤写成**确定性 test case**（E2E spec / 单测 / API 回归脚本），失败断言锁定观察到的真实行为 | 一个**红的**测试，精确表达"bug 在这里" |
| 3. 修复 | 改业务代码、测试代码或配置 | 代码 / 配置变更 |
| 4. 验证 | **同一个 test case** 由红变绿 | 修复正确性的证据 + 永久回归防护 |

**为什么不能跳过固化**：

- 源码分析可能误判——读到的实现 ≠ 运行时行为（框架内部有事件委托 / portal / 动画 / memo / 异步队列等黑盒）；
- 没有固化 test case 的"修复"没有可证伪性——你不知道修的是真 bug 还是想象中的 bug；
- 固化后 red→green 的翻转是最强的修复正确性证据，也是唯一能防回归的形态。

**反模式（禁止）**：

- 读源码 → 猜根因 → 改代码 → 跑原测试看是否还红（原测试可能根本不覆盖该 bug，红绿都不能证明修复）；
- 直接改断言 / 放宽断言让测试变绿（掩盖问题）；
- 反复盲改选择器 / 参数直到通过（无复现 = 无方向，大概率在修错问题）；
- "本地跑通了"就当修好，没留下任何可持续运行的验证产物。

**诊断工具分层**（按成本从低到高，按需升级）：

| 层 | 工具 | 适用 |
|---|---|---|
| L1 | 框架内诊断（测试框架 debug 模式 / 调试器断点） | 首选，常规失败足够 |
| L2 | 独立交互工具（浏览器 DevTools / MCP、curl、HTTP 客户端） | 框架内工具无法解释失败（事件链失效、瞬态 DOM、actionability 拦截、需要绕过框架约束） |
| L3 | 源码分析（Grep / Read） | 任何需要理解"为什么"的失败，配合 L2 做根因定位 |
| L4 | 人工操作（手动浏览器 / 人工 DevTools） | L1-L3 都无法定位时兜底 |

**跨场景示例**：

- **应用 bug**：用户报告某按钮无反应。先用浏览器工具点击观察事件链（复现），再加单测锁定按钮应触发但未触发的回调（固化），再改业务代码（修复），跑单测红转绿（验证）。
- **生产事故**：日志显示某 API 偶发 500。先用日志 + 复现脚本构造最小请求体（复现），把请求写进集成测试套件（固化），定位并修根因如数据库连接泄漏（修复），CI 跑测试红转绿（验证）。
- **测试失败/flaky**：先用 debug 模式或浏览器工具在失败点观察实际状态（复现），把触发 flaky 的条件写成独立用例（固化），按根因处置（修复），用例由红转绿（验证）。

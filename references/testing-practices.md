# 测试协作详情

> SKILL.md §5 的完整展开：E2E 定位与正确流程、测试数据后端约束、断言漂移与全链路验证、平台专属用例处置的完整说明。开展测试编写、E2E 调试、测试数据构造时阅读。

## 5.1 预设环境就绪，改后即跑

做测试相关工作时，默认用户指定的测试环境、浏览器/运行器和认证状态均已就绪。Agent 应直接运行测试验证，而不是先检查环境或自行启动服务。若发现环境未就绪（连接失败、未登录等），**提醒用户打开**，而不是自行启动或跳过。

## 5.2 每次修改后必须跑测试

- 每次修改测试用例或页面对象后，**必须直接运行测试确认是否通过**。
- 不允许只做静态检查就结束。
- 全量执行时间长，验证问题时**尽量只跑单一测试**（指定文件或过滤条件），不要动辄跑全量。

## 5.3 需要查看运行态时使用浏览器/运行器调试工具

当需要独立了解程序运行态（如浏览器 DOM 结构、页面状态、测试执行上下文等）时，使用当前项目约定的调试工具或 MCP 连接运行实例查看，而不是依赖猜测或静态推断。

## 5.4 E2E 的定位：回归守护而非功能调试

新功能、迁移面板或重构后的代码，**必须先手动验证功能正常**（浏览器走通主流程），确认 API 请求/响应、UI 交互、数据流转均符合预期后，再编写 E2E 测试。

E2E 测试的定位是**回归守护**——确保已有功能不被后续变更破坏。它不是功能调试工具：用 E2E 调试未验证的新功能，会同时面对"功能可能没写对"和"测试可能没写对"双重不确定性，浪费大量时间在定位问题源头。

正确流程：

1. 启动应用，用浏览器手动走通主路径；
2. 确认 API 请求 URL、参数、响应均正确；
3. 确认 UI 交互（表单校验、弹窗开关、列表刷新）正常；
4. 功能确认无误后，编写 E2E 测试做回归守护。

## 5.5 测试数据必须满足后端真实约束

使用真实 API 的自闭环测试（创建→验证→删除），测试数据**必须满足后端校验约束**：必填字段、最小长度、格式要求、枚举值范围。否则创建请求被后端静默拒绝，测试可能看到"成功"提示（因为前端错误处理缺陷）但数据实际未创建，级联导致后续编辑/删除用例全部失败。

编写自闭环测试前，应先通过浏览器或 API 工具确认后端对各字段的校验规则，将规则反映到测试数据中。**前端展示的成功状态不可作为数据落地的证据。**

## 5.6 数据断言语义与全链路验证

- **共享环境断言容忍漂移**：服务器数据断言应使用包含语义（集合 ⊇、计数 `>=`、字段存在即可），禁止全等断言与精确行数。共享测试环境可能存在脏数据，且服务器版本可能超前/滞后，断言必须容忍合理的漂移。
- **全链路数据契约**：从前端到后端接口再到数据库，关键字段需全链路验证。测试不应只断言 UI 展示，还应通过直连后端的辅助手段确认数据状态符合预期，确保"界面看到的数据"与"服务器真实数据"一致。

## 5.7 平台专属用例：自判环境 + 带理由跳过

写给特定平台的用例，在非目标平台上必然失败（如仅 macOS 能构造的设备通道，在 Linux/Windows 上按设计拒绝）。正确姿态是**用例留在原文件、自判环境后带理由跳过**，而不是把用例改到全平台变绿：

- 用例开头判断环境，不可执行时优雅退出。Go：`runtime.GOOS` 判断 + `t.Skip("理由")`；
- 跳过理由取**产品侧同款措辞**（如构造器拒绝时的错误文案），`go test -v` 输出里 SKIP 自带解释——覆盖变化有声可查，不静默消失；
- 处置极小且纯增量：只加守卫与理由，不触碰既有用例的构造与断言。

两个反例：

- **改写成 fake 替身求跨平台通过**：测试语义从「验证真实接线」漂移为「验证一个不存在的路径」，被放弃的真实覆盖还得另建文件承接；
- **为混装文件里的单条用例拆 `//go:build` 平台文件**：文件级标签只适用于整个文件都是平台专属的情形；混装文件里会误伤跨平台用例，且跳过在非目标平台上无声无迹。
